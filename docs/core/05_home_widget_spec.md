# Home Widget Spec

本文件定義 Reminder App 第一版 iOS / Android Home widget 的產品語意、資料來源、snapshot 架構、行為邊界與後續實作計畫。

本文件不可取代 `docs/core/04_core_model_spec_v1.md`。Home widget 必須跟隨現有 Home section semantics，不能建立另一套 native-only domain 或 status 推導邏輯。

## 1. Product Purpose

Home widget 的目的，是讓使用者在手機主畫面以最少負擔看到今天最需要注意的生活責任，並對可安全直接處理的項目做快速操作。

第一版 widget 應保持：

- minimal
- compact
- calm
- low decoration
- no raw enum values

Widget 不是完整 Home page，也不是管理入口。它只呈現 Home 已整理好的三個摘要 tab，並把需要 business logic 的工作交回 Flutter / domain / repository layer。

## 2. Supported Platforms And Size

### 2.1 Platforms

第一版支援：

- iOS 17+
- Android 12+

### 2.2 Widget Size

第一版只提供一種 large widget。

不提供 small / medium widget，不提供可設定多種 widget layout，也不提供不同 Pack 的 widget instance 設定。

## 3. Tabs

Large widget 內有 3 個 tab。Tab 切換是 widget UI state，不改變 app domain data。

| Tab | User label | Home mapping |
| --- | --- | --- |
| needsHandling | `需要處理` | Same entries as app Home DANGER / needs handling section |
| attention | `要留意` | Same entries as app Home WARNING / attention section |
| todayCompleted | `今天已完成` | All entries shown by app Home today completed section |

### 3.1 需要處理

`需要處理` 必須使用和 app Home danger section 相同的資料語意。

Data source mapping:

- Use `HomeRepository.watchDangerAttentionEntries`.
- The entry set is mixed-domain `HomeAttentionEntry` data.
- It includes danger `Item` entries and danger `Resource` entries.
- `StageTracker` itself must not enter this tab.
- `StageOccurrence` remains outside the first widget version.

### 3.2 要留意

`要留意` 必須使用和 app Home warning section 相同的資料語意。

Data source mapping:

- Use `HomeRepository.watchWarningAttentionEntries`.
- The entry set is mixed-domain `HomeAttentionEntry` data.
- It includes warning `Item` entries and warning `Resource` entries.
- `StageTracker` itself must not enter this tab.
- `StageOccurrence` remains outside the first widget version.

### 3.3 今天已完成

`今天已完成` 必須使用和 app Home today completed section 相同的資料語意。

Data source mapping:

- Use `HomeRepository.watchTodayCompletedEntries`.
- Include all Home today completed entries:
  - `ItemActionRecord(done)` entries that are still effective.
  - `ResourceActionRecord(refilled / adjusted)` entries.
  - acknowledged `StageRecord` entries.
- Follow current Home repository ordering.
- Do not independently query action tables from native widget code.

## 4. Row Layout

Each row displays:

- title
- status text
- optional display icon such as a Pack emoji
- action area

The row must use Flutter-generated display strings. Native code must not show raw enum values such as `danger`, `warning`, `itemDone`, `resourceRefilled`, or `stageAcknowledged`.
`displayIcon` is presentation-only metadata. Native code may render it when present, but must not infer domain status or action eligibility from it.

### 4.1 Title

Title comes from the Home entry:

- Attention rows use `HomeAttentionEntry.title`.
- Today completed rows use `TodayCompletedEntry.title`.

### 4.2 Status Text

Status text is generated by Flutter before writing the widget snapshot.

Recommended mappings for first implementation:

- Item attention rows reuse the same presentation logic as Home item cards, including compact trailing labels such as due / elapsed state.
- Resource attention rows reuse existing resource formatter output such as remaining quantity or remaining days.
- Today completed rows use user-facing action text:
  - item done: `完成`
  - resource refilled: `已補充`
  - resource adjusted: `已修正`
  - stage acknowledged: `知道了`

Native code only renders `statusText` from the snapshot.

### 4.3 Action Area

Action area behavior depends on row type and tab.

For `需要處理` / `要留意`:

- Item rows show button text `完成`.
- Pressing `完成` directly completes the entry through Flutter action handling.
- Resource rows are shown but do not expose direct `完成` in v1.
- Resource direct action is intentionally omitted in v1 because existing Home semantics require refill / adjust flows, not a generic complete action.

For `今天已完成`:

- Item done rows show button text `復原` only when `TodayCompletedEntry.canUndo == true`.
- If `canUndo == false`, do not show the `復原` button.
- Resource completed rows do not show `復原` in v1.
- Stage acknowledged rows do not show `復原` in v1.

## 5. Snapshot Architecture

Native iOS / Android widget code must not read Drift directly.

Native widget code must not:

- open the app SQLite / Drift database
- query Drift tables
- duplicate `ItemStatusService` or `ResourceStatusService`
- calculate Home section membership
- calculate warning / danger status
- infer `canUndo`
- display raw enum names

Native widget code may only read a Flutter-generated widget snapshot.

Future remote-backed boundary: remote-backed items may be eligible for widget display only after Phase 5 local mirror and sync outbox are implemented. Widget must never call Supabase directly. Widget actions for remote-backed items must write local pending actions / outbox.

Phase 5E boundary: even though remote-backed item mirrors can appear on the app Home screen, generated widget snapshots must still exclude remote-backed item attention / completed rows, and stale widget actions targeting remote-backed items must fail closed. Widget display/action support for remote-backed items remains Phase 5F work.

### 5.1 Snapshot Storage

Flutter-side boundary implementation writes a small JSON snapshot through `HomeWidgetSnapshotStore`.

Current implementation:

- `FileHomeWidgetSnapshotStore` stores `home_widget_snapshot.json`.
- On Android, the file is stored under the Flutter application support directory.
- On iOS, the store asks the native `reminder_app/home_widget` MethodChannel for the App Group container path and writes the same JSON file there.
- If the iOS App Group path is unavailable, the store falls back to the Flutter application support directory so app startup remains safe.
- Android native widget rendering reads the same file from `context.filesDir/home_widget_snapshot.json`, matching `path_provider_android` application support storage.
- iOS native widget rendering reads the App Group file at `home_widget_snapshot.json`.

Native integration writes or reads the same semantic snapshot through platform-appropriate storage:

- iOS: implemented with an App Group shared container file.
- Android: the app-private application support file is sufficient for the AppWidget provider.

The Android native reader expects `context.filesDir/home_widget_snapshot.json`. Flutter writes the file through `path_provider` application support storage, which is expected to map to the app files directory on Android. The iOS native reader and Flutter writer both use the App Group container file `home_widget_snapshot.json`.

### 5.2 Snapshot Shape

The Flutter-side snapshot uses this semantic shape:

```dart
HomeWidgetSnapshot {
  schemaVersion: int
  generatedAt: DateTime
  tabs: List<HomeWidgetTabSnapshot>
}

HomeWidgetTabSnapshot {
  id: String
  label: String
  rows: List<HomeWidgetRowSnapshot>
  emptyText: String
}

HomeWidgetRowSnapshot {
  id: String
  sourceType: String
  sourceId: int?
  actionRecordId: int?
  title: String
  statusText: String
  displayIcon?: String
  actionKind: String?
  actionLabel: String?
  canAct: bool
}
```

The serialized snapshot should use stable string identifiers for native rendering, but those strings are protocol values, not user-facing text.

### 5.3 Snapshot Refresh

Flutter should regenerate the snapshot:

- after app launch
- after app resume
- after complete / undo actions from the widget
- after HomeRepository data changes while the app is active
- after relevant repository mutations that affect Home sections

The snapshot should include `generatedAt` so native code can detect stale data.

## 6. Responsibilities

### 6.1 Flutter Side

Flutter owns:

- reading Home data from `HomeRepository`
- preserving Home ordering
- status calculation
- user-facing label formatting
- action eligibility, including `TodayCompletedEntry.canUndo`
- building and writing the widget snapshot
- executing complete / undo through repository methods
- refreshing the snapshot after actions

Relevant existing sources:

- `HomeRepository.watchDangerAttentionEntries`
- `HomeRepository.watchWarningAttentionEntries`
- `HomeRepository.watchTodayCompletedEntries`
- `HomeAttentionEntry`
- `TodayCompletedEntry`
- `ItemRepository.markDone`
- `ItemRepository.undoDone`
- existing formatter and view model patterns for user-facing status text

### 6.2 Native Widget Side

Native widget code owns:

- rendering the latest snapshot
- switching tabs inside the widget
- invoking complete / undo action intents or deep links
- showing empty, stale, loading, and failure fallback states
- requesting native widget timeline / AppWidget refresh after snapshot changes

Native widget code does not own domain interpretation.

### 6.3 Android AppWidget Implementation

Android v1 uses native `AppWidgetProvider` + `RemoteViews` for one large home screen widget.

Implemented Android behavior:

- `ReminderHomeWidgetProvider` reads only `home_widget_snapshot.json`; it does not read Drift or calculate Home status.
- `ReminderHomeWidgetActionReceiver` persists selected tab state in Android `SharedPreferences` and refreshes widget instances.
- Missing, corrupt, unsupported, or stale snapshots show a safe fallback with an app-open tap target.
- `MainActivity` asks existing widget instances to redraw on resume / pause so the widget can pick up the latest snapshot after the app has opened.
- 完成 / 復原 buttons are wired to receiver actions that store a pending action in app-private `SharedPreferences`, then open the app.
- `MainActivity` exposes `readAndClearPendingAction` and `reloadHomeWidgets` through the existing `reminder_app/home_widget` MethodChannel.
- `MainActivity` also persists legacy `homeWidgetAction` / `homeWidgetEntryId` extras, then removes those extras so the same launch intent cannot be consumed repeatedly.

Remaining Android bridge limitation:

- Direct background completion / undo is not implemented yet because there is no background Flutter engine bridge.
- Android widget actions require the app to open / activate. Flutter then consumes the pending action and calls `HomeWidgetActionService`.

### 6.4 iOS WidgetKit Implementation

iOS v1 uses a native iOS 17+ WidgetKit extension with one `.systemLarge` widget.

Implemented iOS behavior:

- `ReminderHomeWidgetExtension` reads only `home_widget_snapshot.json` from the App Group container; it does not read Drift or calculate Home status.
- `ReminderHomeWidgetView` renders the three snapshot tabs, tab counts, selected-tab rows, empty states, and missing / stale / corrupt fallbacks.
- `SwitchHomeWidgetTabIntent` persists selected tab state in App Group `UserDefaults` and reloads the widget timeline.
- The Flutter app exposes a small `reminder_app/home_widget` MethodChannel for App Group container lookup and `WidgetCenter` timeline reloads.
- On iOS 17, row action controls open Runner through the `reminderapp://home-widget-action` URL with action metadata in the URL query. Runner writes that metadata into the same App Group pending-action keys before Flutter consumes it.
- `CompleteHomeWidgetEntryIntent` and `UndoHomeWidgetEntryIntent` remain safe AppIntent transport helpers: they write pending action metadata, including a nonce, to App Group `UserDefaults`, force the App Group defaults handoff, and reload the timeline when invoked.
- `AppDelegate` exposes `readAndClearPendingAction` through the existing `reminder_app/home_widget` MethodChannel.
- Runner registers the `reminderapp` URL scheme only as an activation target; Swift still does not mutate reminders. Flutter reads the pending action from App Group storage and performs the repository mutation.

Required iOS setup:

- Runner and `ReminderHomeWidgetExtension` both declare the App Group entitlement `group.com.example.reminderApp.homeWidget`.
- The same App Group must be enabled manually in Apple Developer / Xcode for the app id and widget extension id.

Remaining iOS bridge limitation:

- Direct background completion / undo from AppIntent is not implemented yet because WidgetKit does not directly invoke the Flutter repository layer.
- iOS widget actions require the app to open / activate. Flutter then consumes the pending App Group action and calls `HomeWidgetActionService`.
- The iOS 17 visible row action path uses a URL-backed widget tap target because explicit `OpenURLIntent` AppIntent results require a newer iOS SDK availability than the widget's iOS 17 target.

### 6.5 Shared Pending Action Bridge

Flutter owns action consumption through `HomeWidgetPendingActionService`.

Implemented shared bridge behavior:

- Native Android / iOS stores only transport metadata: action kind, entry id, source platform, created timestamp, and nonce.
- Flutter reads and clears the pending native record through `HomeWidgetNativeBridge.readAndClearPendingAction`.
- Flutter validates the action and entry id before execution.
- `complete` delegates to `HomeWidgetActionService.completeEntry`.
- `undo` delegates to `HomeWidgetActionService.undoCompletedEntry`.
- Unsupported, malformed, stale, or no-longer-actionable rows fail closed.
- Flutter refreshes the snapshot after valid, invalid, duplicate, successful, and failed consumption.

Duplicate prevention:

- Native records are cleared before Flutter executes the repository action.
- Each pending action carries a nonce where the platform can provide one.
- Flutter keeps an in-memory consumed nonce set for the current process to ignore repeated native callbacks or repeated delivery of the same record.
- Android removes launch extras after persisting them so hot restart / repeated lifecycle delivery cannot recreate the same pending action.

## 7. Action Flows

### 7.1 Switch Tab

1. User taps a widget tab.
2. Native widget updates widget-local selected tab state.
3. Native widget re-renders rows from the same snapshot.
4. No Flutter repository mutation occurs.

### 7.2 Complete Item

1. User taps `完成` on an Item row in `需要處理` or `要留意`.
2. Native widget stores a pending `complete` action containing the widget row id, then opens / activates the app.
3. Flutter reads and clears the pending action.
4. Flutter action handler validates the target row against the latest snapshot.
5. Flutter calls `ItemRepository.markDone(itemId, doneAt: current effective date)`.
6. Repository records the Item action and any linked Resource consumption using existing domain logic.
7. Flutter regenerates the widget snapshot.
8. Native widget reloads and renders the updated snapshot.

If the item no longer exists, cannot be completed, or repository returns `false`, native widget should show a calm failure fallback and refresh from the latest snapshot.

### 7.3 Undo Completed Item

1. User taps `復原` on a today completed Item row.
2. Native widget stores a pending `undo` action containing the widget row id, then opens / activates the app.
3. Flutter reads and clears the pending action.
4. Flutter action handler validates the target row against the latest snapshot.
5. Flutter calls `ItemRepository.undoDone(actionRecordId, revertedAt: current effective date)`.
6. Repository restores the Item snapshot and reverses linked Resource consumption using existing domain logic.
7. Flutter regenerates the widget snapshot.
8. Native widget reloads and renders the updated snapshot.

If `TodayCompletedEntry.canUndo` is false, the snapshot must not expose the `復原` action. If the action later becomes invalid, Flutter returns failure and native refreshes.

## 8. Stale Data And Failure Fallbacks

The widget must remain calm and readable when data is unavailable.

Fallback rules:

- Missing snapshot: show a neutral empty state asking the user to open the app once.
- Corrupt snapshot or unsupported schema version: show a neutral fallback and request refresh on next app launch.
- Stale snapshot: continue rendering the snapshot with a subtle stale indication if supported by platform constraints.
- Empty tab: show a short user-facing empty message for that tab.
- Action in progress: prevent duplicate taps for the same row when possible.
- Action failure: show a brief platform-appropriate failure state and reload the snapshot.

Native fallback text must be user-facing Traditional Chinese, not protocol values.

## 9. Limitations Of First Version

First version intentionally does not include:

- small or medium widget sizes
- per-Pack widget configuration
- upcoming StageOccurrence tab
- Resource refill / adjust from widget
- Stage acknowledge from widget
- undo for Resource or Stage completed rows
- native Drift database access
- native status calculation
- background-only widget action execution
- adding new dependencies before implementation justification

## 10. Testing Plan

### 10.1 Automated Tests

Automated tests should cover:

- Snapshot builder maps danger rows from `HomeRepository.watchDangerAttentionEntries`.
- Snapshot builder maps warning rows from `HomeRepository.watchWarningAttentionEntries`.
- Snapshot builder maps completed rows from `HomeRepository.watchTodayCompletedEntries`.
- Snapshot row ordering matches HomeRepository ordering.
- Snapshot never exposes raw enum values as user-facing text.
- Item attention rows expose `完成`.
- Resource attention rows do not expose unsupported direct completion.
- Completed Item rows expose `復原` only when `TodayCompletedEntry.canUndo == true`.
- Complete action delegates to `ItemRepository.markDone`.
- Undo action delegates to `ItemRepository.undoDone`.
- Snapshot refresh occurs after complete and undo.
- Pending widget action parsing covers Android and iOS transport records.
- Pending widget actions are cleared before execution.
- Duplicate pending widget actions are ignored by nonce.
- Native renderers handle missing, corrupt, stale, empty, and action-failure states.

### 10.2 Manual QA

Android 12+:

- Launch the app once so Flutter writes `home_widget_snapshot.json`.
- Add the large Reminder widget.
- Verify tabs, counts, selected-tab switching, row text, empty states, and stale / missing fallback.
- Tap `完成` on an actionable item row and verify the app opens, the item completes once, and the widget refreshes.
- Tap `復原` on an undoable completed item row and verify the app opens, the item undo runs once, and the widget refreshes.
- Resume / relaunch repeatedly after each action and verify the same action is not repeated.

iOS 17+:

- Enable App Group `group.com.example.reminderApp.homeWidget` for Runner and `ReminderHomeWidgetExtension`.
- Launch the app once so Flutter writes the App Group snapshot.
- Add the large Reminder widget.
- Verify tabs, counts, selected-tab switching, row text, empty states, and stale / missing fallback.
- Tap `完成` / `復原` and verify the app opens, the repository action runs once, and WidgetKit reloads.
- In the Xcode console, verify the AppIntent write log, Runner URL open log, pending action read log, Flutter action consumption, and WidgetKit reload request.
- Resume / relaunch repeatedly after each action and verify the same pending action is not repeated.
